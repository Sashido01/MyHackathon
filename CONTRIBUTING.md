# Участие в разработке / Contributing

Документ описывает начальные правила работы небольшой команды (3 человека). Их можно уточнить после получения кейса.

## Доступ

Для записи в репозиторий участник должен быть приглашён владельцем через **Settings → Collaborators** и принять приглашение. GitHub-профили других участников будут опубликованы только после подтверждения.

## Начало работы

```powershell
git clone https://github.com/Sashido01/MyHackathon.git D:\MyHackathon
Set-Location D:\MyHackathon
```

Это путь владельца проекта в Windows. Остальные участники могут клонировать репозиторий в удобную для себя папку. Если папка уже существует, повторно клонировать репозиторий в неё не нужно.

## Порядок изменений

1. Сначала опишите задачу в GitHub Issue или обсудите её в команде.
2. Получите свежую версию `main` и создайте рабочую ветку (например, `docs/readme`, `feat/demo`, `fix/validation`).
3. Делайте небольшие логичные коммиты с понятными сообщениями.
4. Откройте Pull Request с описанием изменений и способом проверки.
5. По возможности попросите другого участника посмотреть PR перед объединением. Самостоятельное объединение допустимо, если команда заранее это согласовала.
6. Не переписывайте общую историю (`push --force`) без явного согласования.

Рекомендуемый формат коммитов — **Conventional Commits**: `feat: ...`, `fix: ...`, `docs: ...`, `test: ...`, `chore: ...`. Это командная конвенция, не доказательство выполнения каких-либо автоматических проверок.

## Проверка качества

Пока стек неизвестен, команды линтера и тестов не определены. После выбора кейса команды должны появиться в README и CI и выполняться одинаково у всех участников. Не отмечайте тесты как пройденные, если их не запускали.

## Локальные проверки репозитория

При наличии Python 3.11+ из корня репозитория выполните:

```powershell
python scripts/check_repo.py
python -m unittest discover -s scripts/tests -v
```

Первая команда проверяет окончания строк, наличие завершающего перевода строки и относительные Markdown-ссылки. Вторая выполняет тесты самой проверки. Отдельное задание CI использует Gitleaks для поиска потенциальных секретов в Git-истории; отсутствие находок **не гарантирует** отсутствия всех секретов. Проверки приложения добавим после получения кейса.

Подробности: [docs/development-setup.md](docs/development-setup.md).

## Публичность и безопасность

- Не добавляйте токены, пароли, приватные ключи, `.env`, личные данные и внутреннюю переписку.
- Не публикуйте материалы кейсодателя, пока их публичное использование не разрешено.
- Используйте примеры без персональных данных и вымышленные данные только с явной пометкой об этом.
- Следите за лицензиями сторонних библиотек, изображений, шрифтов и датасетов.
- Про проблемы безопасности сначала сообщайте приватно — см. [SECURITY.md](SECURITY.md).

## Общение и признание вклада

Сохраняйте уважительный тон; обсуждайте технические решения и результаты, а не личности. В [AUTHORS.md](AUTHORS.md) фиксируются реальные вклады; Git-коммиты и PR помогают подтвердить их.
